# elise-frontend-web: screens

What each screen shows and why. Read it with `DESIGN.md` (tokens, layout, components, shared patterns, the design standard) when you review or change one of these screens. Every rule here is as mandatory as the rules there.

- **Overview** leads with what to do, for readers who are not engineers as much as for engineers, and puts the scan history after it. 32px between cards, and the same header on every card (a 15px title and one 14px line).
  1. **The brief** (`RepoOverviewBrief`, a `ScanOverview` slot from the route, because the scan module does not import the repository module: `oxlint.config.ts` enforces the direction). Three parts, from the repository list alone (the counts of each default branch):
     - **The ship answer**, an `Alert`: "Not ready to ship" (red), "Almost there" (amber) or "Ready to ship" (green), one line naming the repository of the urgent items and the repositories whose latest scan failed, when the latest scan was, and "Start with the first item", which opens and scrolls to the first group. The words come from `overviewVerdict`.
     - **Four counts** in one card (open problems with severity dots and "not rated", came back, waiting for a person, possibly out of date), coloured by meaning (a 0 is muted). Each is a button that opens and scrolls to its group ("See all 10 below", "See the 3 findings").
     - **What to do, most urgent first** (a `CardHeader` and `CardContent`): one row per group from `overviewActions`, in the order came back, serious (critical and high), needs a person, missed by the latest full scan, latest scan failed, lower risk, never scanned, and the budget. Each row has a coloured left bar, a plain-words title with a count, badges for how urgent it is ("Urgent", "Needs a look", "When convenient"), who it is for ("For an engineer", "For a reviewer", "For an admin") and where (the repository, or "N repositories"), one sentence on what it means, a button to the repository with the most of that problem ("Review the regression in checkout-api"), and "Show where", which lists each repository with its count and an "Open" link. A finding can count in two groups (a serious problem that came back is in both), and each group states its own count. The lower-risk groups (lower risk, never scanned) stay behind "Show N lower-priority actions", so the urgent ones are never pushed down; a count button that points at a folded group unfolds it. With no repository the card says nothing is watched and offers "Add repository"; with nothing to do the answer is "Ready to ship" and the list card is not shown.
     - The budget joins the list only when the engine says it applies (`budgetApplies` is true: an account with no plan and no key of its own, or an admin override) and 90% or more is spent or held; its button shows only to a login that can change the budget. Under the Runner plan scans run on the customer's own computer and there is no budget to watch.
  2. **Running now**, only while a scan is queued or running: one row each with the repository, the branch and commit (`ScanOrigin`), the status and when it started, linking to the live report. It is gone when nothing runs, because the "In progress" state is also in the sidebar and the scan list behind it polls only while a scan is active.
  3. **Recent scans** (four rows with branch and commit; every status, succeeded included, is a pill) beside the success rate (a ring), then the scan activity across the full width.
  4. The monthly budget and the credit card, only when they apply: the budget card hides itself unless `budgetApplies` is true, and the credit card unless the plan holds credit. A row with neither is not drawn.
  - The scan-count tiles, the severity breakdown card and the old "Where to look first" list were removed: the ring already says succeeded and failed, the count strip carries the severity dots, and the action list says where to look.
  - **Colour follows the status on this page**: the ring, the succeeded figure and the succeeded bars are green, red appears for a failure (the failed count, the failed bars, an urgent group, a used-up budget), amber for what needs a look, blue for a running scan and what can wait, and the severity dots carry the findings.
- **Security status** (`/summary`, `modules/summary`; every signed-in member, linked under Overview) is a read-only page for people who watch the workspace and do not work in the findings. A **Watcher** (a login that holds the Summary Power and not the Dashboard Power, `isWatcher`) sees nothing else: every other page redirects to `/summary`, the sidebar lists only Security status, the topbar has no "New scan" button, and the layout does not load the scan list. It answers "where does each repository stand" before anything else: a header, a `RepoSummaryStrip` (open findings as the lead number, came back, needs a person and not in the latest full scan), then one **Repositories** card with a row per repository, most urgent first (`rankRepos`). A row with something open reads as a link (a chevron, the repository and its default branch, then the severity dots, "N need a person" for the open findings the agent could not confirm and so carry no severity, "N open" and a status pill) and opens that repository's page; a repository with nothing to read is a plain row. There is no accordion.
  - **Repository page** (`/summary/$repoId`, `modules/summary`; same audience; the id is the repository's, and one this account does not hold shows the app's "Page not found"): the breadcrumb is Security status, then the repository. A header with the repository name, its default branch and its status pill; the same `RepoSummaryStrip`, for this repository alone; then an **Open findings** card. Every open finding on the default branch is written out in full, none hidden: a severity badge and a state badge ("Confirmed", "Came back" or "Needs a person to check"), a "Copy link" button, the title (`h3`), and "What could happen", "How it gets fixed" and, for an unconfirmed one, "What a person needs to check". Each finding has its own address, `/summary/$repoId#finding-<id>`: "Copy link" puts it on the clipboard, and opening it scrolls to the finding and marks it with a 3px bar in `--primary`. More than a page of findings loads with "Show more findings".
  - Each row names the repository and its default branch, and ends with one status: **Clear** (nothing open), **Needs attention** (anything open, with a red "came back" count when a fixed problem returned) or **Not scanned yet**. The status comes from the repository list alone (`repoStatus`); there is no ship verdict yet, because it needs one extra request per repository.
  - Only a row that needs attention opens. The first such row starts open. Its findings load when it opens (the default branch, open findings only; fixed, dismissed and accepted risks are not shown), so the page itself is one cached request.
  - A finding shows its severity, its state in plain words (Confirmed, Needs a person to check, Came back) and its title. **Details** holds the impact and the fix, plus what a person needs to check when the finding needs one. Evidence, file paths and the actor are never shown, and nothing on the page links into the technical screens or changes anything.
  - Loading is a skeleton shaped like the page; a repository whose findings fail to load shows the error inside its own row with "Try again". The wording is the scan's own, so it is still written for engineers: a plain-language rewrite is not part of this page.
- **Stat card** (`ShellStatTile`, on `/repos` and the scan report): label and an icon tile (tinted by meaning) on one row, a 34px number, then one muted line of context derived from real data. A value of 0 is muted so the tiles with something to act on stand out.
- **Scan activity chart**: a stacked bar per day for the last 14 days (succeeded in `mark-success`, failed, in progress), dashed gridlines with a value axis, and a tooltip on every bar that lists the day and its counts. Each bar is a labelled button, so keyboard and screen-reader users get the same numbers. The data is derived from the scans list; the chart needs no endpoint.
- **Success ring**: an SVG ring with the percentage in the middle and a green arc, then succeeded and failed as figures. The succeeded figure is green and the failed figure red, each only while it is above 0.
- **Severity chart** (not on the overview; kept for a screen that needs it): a segmented bar for share, then one row per severity with dot, label, `Progress` bar, count and percent. Colour is never the only signal: every row has a text label and a number.
- **Lists**: a repository is shown as muted `owner/` plus the `name` in full weight. Times are short (`Nov 8, 10:12 AM`) in muted tabular numerals.
- **Private repositories carry one marker, the same everywhere** (`GithubPrivateBadge`): a "Private" outline badge with a lock in headings (the repository list, the repository and branch pages, the scan report), and the lock alone, small and muted, in dense rows (the scan lists and the sidebar tree), with "Private repository" for a screen reader and on hover. A branch has no marker of its own: it is private because its repository is. A public repository, and one no connection covers, show nothing, because the marker is the exception (`DESIGN.md` Restraint). It reads the repository's last answer from GitHub (`isPrivate`) in the repository screens, and the scan's own answer in the scan screens, so an old scan keeps what was true when it ran. The Files list does not show it yet.
- **Status panels** on a scan page are `Alert`s: failed is the destructive variant with the engine's message; queued and running is the info variant with a spinner.
- **Scan report** (`ScanDetail`) says what one scan found: its tiles, what changed, its findings. It has no Ready-to-ship card: the answer weighs every scan of the commit and the team's decisions, so it lives on the branch page, one click away through the branch chip or the breadcrumb. The breadcrumb names the scan by when it started ("Scan of Nov 17, 12:43 PM"), because two scans of one commit share the commit; there is no separate "All scans" link above the header.
  - **Header**: the repository (muted `owner/`, the name in full weight) and the Private badge when it applies, then the branch as a chip (the way to that branch's history, with a button that opens the branch on GitHub), or "One-off scan" for a pasted commit with a link to the repository's history. Under it one calm line, as on the branch page: the status, when it started, how long it took, the coverage a full scan asked for ("Coverage Balanced"), and "Commit" with the short sha as a link to GitHub. "Scan this branch again" (or "Scan again" for a one-off scan) sits on the right and opens the new-scan dialog on that repository and branch. Model and effort are not in the header. An upload Scan's chip names its zip (with an archive icon, or "<file> (file removed)" once the zip is gone) and leads to the app's History, with no link out; the line reads "Zip hash" and the short SHA-256 instead of a commit, and the button reads "Scan a zip again". The scan lists name the zip the same way under the repository, and **Scans of this branch** becomes **Scans of this app** with a "Zip" column. An app's page (the hidden `upload` branch) has no branch switch, no GitHub links and a "Zip" column in Recent scans; its header line names the latest zip, "Scan a zip" opens Upload on the app, and a card under the header lists its zips (as in the picker, upload and remove) and "Remove app" (a dialog says every zip is deleted and the audits stay on the Scans page; the app then leaves the Repos list and the page goes to `/repos`).
  - **Body, in order**: the four summary tiles (findings with severity dots, needs a person, new since last scan, cost; a scan that ran on a Runner reads "What it would cost" and says it ran on that computer, so nothing was billed); two alerts when they apply, **came back after being fixed** (red) and **not re-checked by this scan** (amber, treat as still open; both for older scans only, which the branch page no longer words this way); the **What changed** card, which groups findings as came back, new, not re-checked, still open and fixed, each group saying what it means and what to do; the findings table, whose rows open a side sheet with the impact, evidence, suggested fix and what to check in one column (the first cell stacks the severity and, only for a finding that is not confirmed, its state; Where shows the file name and line over its folder, as on the branch page); **Scans of this branch**, the latest five scans of the same branch with this one marked and not a link, hidden for a one-off scan, for a branch with no other scan, and in the demo screens; **Run details**, a closed card with the kind of review, the model and the effort; and the **Files** tabs.
  - **A scan that ran as less than it asked for** (a Runner Scan whose `profileMet` is a smaller profile, or `none`) shows a warning `Alert` above the tiles, decided by `scanProfileNote`: "Asked for Exhaustive. Ran as Balanced." (or "Ran as Focused, a single pass.", or "Asked for Exhaustive. Its work did not run." for `none`), then what did not run, that the findings are kept, and that the Scan can be run again on a Runner or in the cloud. A scan that met its profile, and one with no `profileMet` (a cloud scan, a partial scan, an old scan), shows nothing new. The words are Focused, Balanced and Exhaustive, never `quick`, `standard` or `deep`.
  - A scan that is queued, running or failed shows its notice, then Run details. Raw values (`lite`, `low`) never appear as labels: use the option copy in `constants/`.
- **Scan list** and **Files** show a scan's status the same way as every other screen (`ScanStatusBadge`): a pill for every state, a green one for succeeded. The column is "Status" on the list and "Scan status" on Files.
- **Scan list** marks a scan that ran as less than it asked for with a warning pill under its status (`ScanProfileBadge`: an icon and "Ran as Balanced" or "Did not run as asked", so colour is not the only signal; the full sentence is its tooltip). A full scan shows no second pill.
- **Scan list** rows answer "what did it find and cost" without opening: the branch and commit under the repository, findings with severity dots, a "to check by hand" count, review kind and model, cost. Older scans load with "Load older scans"; the header shows `N+` while more exist.
- **Repositories** follow the same rule: decide first, browse second. A repository is a plain heading and each tracked **branch** under it is the link.
  - **List** (`/repos`): the `RepoSummaryStrip` across every repository (open findings as the lead number, came back, needs a person, not in the latest full scan), then one group per repository, sorted by what needs attention. The heading shows scan count, latest status and time. Each branch is a row linking to its page, with a "Default" tag. Only the default branch row shows open counts, because the engine's list carries only those; other rows say "Open the branch to see its findings". A repository with no branch has one "No branch tracked yet" row. "Add repository" opens a dialog (repository link, optional branch names, "n of 25") that scans nothing and checks nothing on GitHub; it is safe to repeat for a repository that exists.
  - **Branch page** (`/repos/$repoId/branches/$branchId`, ids not names): `/repos/$repoId` redirects to the default branch, or to `?branch=NAME` from a list link. The header holds the repository, a branch chip (a "Switch branch" select when the repository has two or more branches), "Open branch on GitHub" and "Scan this branch". The facts are one line under the branch chip: the status pill of the latest full scan, "Latest full scan <time>" (or "Last scan <time>" when the newest scan is the full one), the commit the verdict reads as a short sha linking to GitHub, and the scan count. The latest full scan is the branch's newest scan that weighs in a Verdict (the engine's `fullScanId`); a newer succeeded scan that does not (a partial scan, one that met no profile) adds "Newer scan <time> (not full)" after "Latest full scan <time>" or "No full scan yet", and carries a "Not a full scan" badge in the scan history. Under the header, the `RepoSummaryStrip` counts this branch alone (open findings with severity dots, came back, needs a person, not in the latest full scan), and the commit's ship answer is its first, wider cell (`ScanVerdictCell`), so the answer and the counts it rests on read as one row at a glance; it replaces the separate Ready-to-ship card and the amber "not in the latest full scan" alert. With the answer in the row, the open count is a plain cell, not the lead, and the other notes are short ("Not in full scan" for the last label) so five cells fit one row. The red "came back" alert stays, under the strip. Findings open in the side sheet (impact, evidence, fix, state, where first seen or fixed, and the decision select, also kept inline on each row). The page has one list of findings, "Findings on this branch", which opens on "Needs action". It is the merge of every succeeded scan of the branch: each row says which scan first saw the problem and which last saw it, each a link to that scan, and marks "Not in the latest full scan" when the branch's latest full scan did not see it (the sheet links that scan). A row's first cell stacks its severity ("Not rated" when the scan could not confirm it), its status only when it is not plain Open (the decision select already says Open), and "Blocks shipping". The Where cell shows the file name and line on one line and its folder, cut from the start, under it; the full path is the tooltip. "Review N problems" moves focus to the list's card, so the next Tab starts there. "Nothing needs action" shows only when no problem is open; no note about old open problems is shown on this page, the repository list, Overview or Security status. The answer cell is not tinted: the answer is a status pill with a dot, like a scan's "Succeeded", red, amber or green. Laid out like the other cells, it reads "Ready to ship? · Commit <sha>" (plain text, no link) as the label, the answer pill in place of a number ("Blocked", "Clear to ship" or "Needs more scans"), one short muted line on what the answer is ("Weighs every scan of this commit and your team's decisions."), then two buttons on one line, "Review N problems" (named "Review N problems in Findings on this branch" for a screen reader) and "Why?" (named "Why this answer?"). The cell holds nothing else: "Why?" opens the "Why this answer?" dialog that starts with "To pass: …" (or, once it passed, why that is advice and not proof), then the rule, how many open problems block shipping and how the list's count differs from the commit's, and the three checks; while the verdict still needs scans, "Run the missing scan" and "Choose options" follow, and once it has every scan it needs there is no scan button. The dialog's description counts the checks met and names what blocks, in the words of the check that failed ("Blocking: 3 not checked by a person yet."), never as a negated label. The cell does not list the open problems, nor the accepted or dismissed ones (the findings list's "Decided by a person" filter holds those, with each acceptance's end date): it gives the commit's open count and says how many of them block shipping (a problem not yet checked by a person always blocks; a critical or high one blocks; a medium one only above three; a low one never), and "Review N problems" jumps to the list. In the list, a row that blocks shipping carries a red "Blocks shipping" mark and comes first. Each finding's row has a "Discussion" button under its decision that opens a side sheet of its own, apart from the finding's sheet: a "Discussion" label over the same header as the finding's sheet (severity, whether a scan confirmed it, its decision, the title, the file and line, and the first lines of what could happen), the comments oldest first, each with the author's initials, name and time (the full date, time and zone in its tooltip), a deleted comment as one small muted line with when it was written and when it was deleted, a line saying there are no comments when only decisions and deleted comments remain, and a composer below, "Comment", that stays disabled while the box is empty and counts up to 4,000 characters; a login that can read but not write sees the thread and a one-line note instead of the composer. The decision stays with the finding's facts: its select says its choice is added to the discussion with the person's name, and the sheet on the scan page has no Discussion button. The findings list has a search and a state filter that shows a count per state. The scan history lists only this branch's scans (older scans with no branch count as the default branch's) and says how many others are hidden. A failed scan says why in one line (`scanFailure`).
  - **No branch**: the page says to run a scan or add the repository again with branch names.
  - **Private repositories** need a connection, which lives on **Connections**, not here. "Add repository" says so beside the link field ("Private repository? Connect GitHub first", a link to `/connections`), gets a picker of the connected repositories above the link field (hidden when there are none), and pasting a link always still works. A private repository shows a "Private" tag next to its name in the list and on its page.
- **Connections** (`/connections`, `modules/github`; visible to every member, and one sidebar item with no children until a second provider exists, as Repositories has no chevron with one repository): where Elise reads code from. A page header, then a **GitHub** card, then a **Repositories Elise can read** card. The GitHub card (and `/github/callback`) shows who the account is connected as (name, "All" or "Selected repositories", the date, a status pill) with a "Manage on GitHub" link on each install (the engine asks GitHub again when its last check is over five minutes old, so a removed or suspended install shows as such), a "Disconnect" button on each install for account admins only (a dialog says Elise stops using it, past scans stay, and that access is removed in GitHub's own settings), and, for admins only, a "Connect GitHub" button (or "Connect another account") that sends the browser to GitHub. Other members read a sentence that asks an admin to connect it. GitHub sends the browser back to `/github/callback`, an admin-only page that saves nothing until the person ticks the notice (code excerpts go to Anthropic) and presses "Finish connecting"; it keeps **Connections** active in the sidebar, its breadcrumb reads Connections, Finish connecting GitHub, and saving returns to `/connections`. The second card lists the repositories the active connections can read (first 100, a "Private" tag on private ones, a search from six rows) and is hidden until a connection is active; it says what to do when the list is empty.
- **Team** (`/team`, `modules/team`; roles that hold `company:team:members:read` (account admin and workspace admin), and anyone else is sent to Overview): who can use the account. A page header ("Who can use this account, and how they are grouped."), then a **People** card and a **Groups** card. People is a table of name and email, role, and Groups, with a "You" tag on the signed-in person, an invite button that opens a dialog (the invite is emailed, and the dialog also shows the link once as a copy), and the invites still waiting, each with its Groups, a "Resend" button (a new email and link; the earlier link stops working) and a "Revoke" button that asks to confirm. Groups lists the named sets of people. A Group grants nothing: access comes from the Role.
- **Settings** (`/settings`, `modules/settings`; roles that hold `company:usage:budget:update` (account admin and workspace admin), and anyone else is sent to Overview, with no sidebar item): how the account pays for scans. In the sidebar it is an item with three pages under it, open while the reader is in Settings (one icon when the sidebar is collapsed): **Budget** (`/settings/budget`), **Providers** (`/settings/providers`, needs `company:usage:anthropic_key:update`, and without it the reader lands on Budget) and **History** (`/settings/history`). `/settings` goes to Budget. **Providers** holds an **Anthropic API key** card: it says whose key the scans use ("Elise's key" by default, or "Your own key" with `sk-ant-…` and its last four characters and the save date), with "Use my own key" (or "Replace key") that opens an inline form (`AnthropicKeyForm`: one masked field, tested with Anthropic before saving, never shown again) and, for an own key, "Remove key". A scan already running keeps the key it started with. Under it, a **Runners** card (`modules/runner`) lists the computers that may run this account's scans: a row for each with its name, one line on what to do next or when it was last seen followed by "Added by <name>." (left out when an older engine sends no name), and a status pill (Waiting for pairing, Code expired, Connected). "Add a runner" opens a dialog that leads with the command `elise-runner login` as copyable text, and below it, for CI and containers, asks one question ("What is this computer called?") and makes a pairing code; the code is shown the pairing code once, large and in mono, with the time it expires and "Copy code"; the list polls every 4 seconds while a code is waiting, so the row turns to Connected when the app pairs. "Remove" asks first and says what stops (a connected computer stops at once). An account with none shows an empty state with the next step. **History** holds a **Recent changes** card: the last 20 changes to the budget and the key, newest first, each with who and when in UTC (a key line shows its last four characters, never the key). **Budget** holds the **Monthly budget** card. The page header reads "What this account may spend on scans each month." Monthly budget leads with the budget in large type and a "Change budget" button that opens an inline form (`UsageBudgetForm`): one dollar field, the allowed range under it ("Between $5.00 and $100.00": at least what the month has spent or holds for running scans, at most the most the account may set), Save and Cancel. Below it: spent this month, held by running scans, remaining, and "Most you can set", with a line to contact Elise for more. A budget line in History reads from what to what (the default is shown as "the default"). A person whose login is gone reads "Someone who has since left". Everyone else still sees the budget on Overview.
- **Sign in, sign up and password reset** (`/signin`, `/signup`, `/forgot-password`, `/reset-password?token=`, `modules/auth`; "Forgot your password?" on sign-in opens the request page, which swaps its form for one line that is the same for every email; the emailed link opens the reset page, and a spent or missing token says so and offers a new link; the invite pages `/invite/$token` share the mark, the corner theme button and the card width): pages with no shell. From 1024px up they are two columns inside a `max-w-6xl` frame: a brand panel (`AuthBrandPanel`: the Elise mark and name, one headline and three plain lines on what Elise does) and the form card (`max-w-lg`, 32px padding, 20px between fields). Below 1024px the panel is hidden and the mark and name sit above the card (`ShellPublicBrand`). The mark (`ShellLogo`) is an "E" of three bars in `--primary` and `--primary-foreground`, so it flips with the theme. A theme button sits in the top right corner (`ShellPublicThemeSwitch`); the pages carry `data-public-page`, so in Moonlight the sky starts at the top, as there is no top bar. The panel and the name take the page header's text halo, so they stay readable on the sky. Field errors say what to type ("Enter your email address."), never the rule that failed; focus moves to the first field with an error. The words are in `modules/auth/constants/auth-copy.ts`.
- **Connect a Runner** (`/device?code=XXXX-XXXX`, `modules/device`; the link `elise-runner login` prints, a page with no shell like the invite pages): where a person approves a Runner that asked to log in from a terminal. Signed out, it sends the person to sign-in with the page and code kept in `?redirect=` (only a path on this site is followed), and sign-in comes back to it. A card says "Check that this code matches the one in your terminal" over the code in large mono, then a warning ("Only approve if you ran `elise-runner login` yourself just now."), then what the terminal sent: OS and CPU, the Runner version and the IP that asked. When that IP differs from the one the person is on now, a second warning says so; it never blocks. The form asks for the account and the computer's name (the terminal's suggestion, editable). Only the accounts where the person's Role holds `company:runners:create` are listed (`/me` powers); one is shown as text and chosen for the person, several are a select with none chosen, and none shows a note to ask an account admin instead of the form. "Approve" then replaces the card with "Your terminal is connected" and says the page can be closed. An unknown, expired, used or missing code shows a plain "This code can't be used" page with no form (the engine does not say which). Under "Approve" sits an outline "Deny": it refuses the login in the chosen account (the first listed one when none is chosen yet), the engine writes the Audit trail entry, and the card is replaced by "Request denied" with a note that the terminal stops waiting.
- **Decisions and status** (`modules/finding`): a finding has two truths, what scans found (open, came back, fixed by a scan) and what a person decided (open, fixed, false positive, accepted risk). The reader gets one answer from both (`findingStatusKey`): a scan that proved a fix wins, then a person's decision, then the scan state. The status badge says it in a word ("Fixed by a scan", "Marked fixed", "False positive", "Risk accepted", "Came back", "Open"), the row shows who decided and when under the decision select, and the sheet opens with a status banner (what happened, who, when, what it means next, and the reason or note). A finding a scan fixed shows no select: no decision is needed. "Marked fixed" says plainly that no scan has confirmed it, and that a later scan finding it again shows as Came back. The repository list filters follow the same grouping as the Open findings tile (needs action, decided by a person, fixed by a scan, every finding), each with a count, so the list and the tile never disagree. **Accepted risk** opens a dialog for a reason and a duration (7 to 90 days), says what will happen in a sentence, and is only enabled for account admins (the option shows "Account admins only" for others). A decision updates the row at once; the counts refresh in the background.
- **Files viewer**: `Tabs` (mono pills, selected pill tinted, arrow-key navigation). A `.md` file renders as formatted text with TanStack Markdown (`ScanMarkdown`: headings, lists, tables and code styled from the design tokens, raw HTML off, links open outside the app); any other file is an inset `pre` with mono text. An empty file shows "This file is empty."
- **Files** (`/files`, `modules/file`): the written reports of every scan, newest first. It lists `REPORT.md`, `FINDINGS-DETAIL.md` and `NEEDS-VALIDATION.md`; the machine-readable files stay on the scan page. The type tabs ("Report", "Finding details", "To check by hand") each show how many files they would list under the other filters, and a type with none is dimmed. A line under the tabs says what the chosen type holds and that dates and times are in UTC; the Saved column is UTC too, so it matches the filters. Filters are a repository select, a branch select (once a repository is chosen), From and To days in UTC, and a repository search sent with Enter. They live in the URL, so a view can be shared. The file name and size never wrap. Below `lg` the Scan and Size columns drop out, and below `md` Branch and Saved too: the repository cell then carries the branch and time. Each Download names its file, repository, branch, UTC time and the end of the scan ID for a screen reader, so no two share a name. "Clear filters" shows once: in the filter row while files are listed, in the empty state when nothing matches.
- **New scan** is a dialog (`ScanNewDialog`), opened from the topbar, from the empty state of the scans list, and as "Scan again" on a repository page. It has a title and no description, and opens on the provider first: a segmented control "Where does the code live?" with GitHub, GitLab, GitLab server and Upload, in the contracts' order (`src/providers/registry.ts`, ADR 0008), on GitHub by default, or on the provider of the repository "Scan again" opened it with. **Upload** has no search: its picker (`src/providers/upload`) says that zips of source code live under a named app, share one History and run on a Runner, then offers an "App" select (the account's upload apps, newest Repos list order, and "New app…") or, with none yet, a "Name of the new app" field and "Create app" (the name rule is the contracts' `UPLOAD_APP_NAME_PATTERN`; a name the account already has, in any case, is refused with a pointer to the list). Under the app, the **Zips** list ("n of 20") with "Upload a zip" and, per zip, its file name, size, upload date and short hash, and "Remove" (a dialog says the zip is gone for good and its audits stay, marked "file removed"). A zip is refused before it is sent, with the engine's own words, when it is not a .zip, over 50 MB, the app's 21st, or its central directory says over 20,000 files, 20 levels or 250 MB unpacked; the account's 500 MB is the engine's to refuse. A line under the list states those limits and that a zip no audit has read is deleted 30 days after upload. Clicking a zip picks it, and "Scan <file>" turns the pick into the card ("Zip <file>"), with no branch select; the request sends `provider: upload`, the app's name, `archive_id` and no `ref`. An engine refusal (such as "This Runner cannot read uploaded zips. Update the Elise Runner app …") stays as an alert in the card as well as the toast. "Scan again" on an upload Scan and "Scan a zip" on an app's page open Upload on that app. Each provider's search lists only its own repositories and reads a pasted link by its own rules. **GitLab** takes a gitlab.com link (groups inside groups, a pasted branch view or `.git` cut off, with or without `https://`), and **GitLab server** a link on any other host; both say under the search that the audit runs on one of the person's Runners with their own git login (GitLab server adds that the Runner clones only from a host in its `settings.json` `gitlabHosts`), their rows carry no Public or Private tag, the card reads "GitLab repository, scanned on your Runner", the branch is typed, "Run on" lists only the connected Runners and takes the first, and with none connected an alert points to Settings, Providers and "Start audit" stays disabled. The request names `provider` only when it is not github. Under the control, for GitHub, one search field ("Search your repositories or paste a GitHub link"): there is no question about public or private. Under it the list shows every repository the account can scan, in a Public group and a Private group, filtered as the person types. A private row has a lock and a "Private" tag, and each row says its last result or that it is connected on GitHub. The arrow keys walk the field and the rows, and Enter takes the first. A pasted GitHub link (with or without `https://`) shows as a "Scan owner/name" row on top, and a link to a repository the account already has answers with that repository, not a duplicate. With no active GitHub connection a line under the list says an admin connects GitHub on Connections to scan a private repository. Until the GitHub connection's repositories have arrived the list shows placeholders (it cannot tell which scanned repositories are private, and rows that move are worse than a short wait), and "Start audit" waits too; a pasted link shows at once. Choosing a repository replaces the list with a card: the repository, "Public repository" or "Private repository" and "Change", which returns to the search, with a labelled "Branch" select on its own row so a long branch name is never cut. The card follows the list: a repository chosen before the connection's repositories arrive is shown as private once they do. The branch select opens on "<default> (default)", then the other branches, then "Other…" to type a branch, tag or commit. A public repository the account scanned reads its branches from the engine, a private one reads them from GitHub through its connection (first 100, with a hint when there are more), and a pasted link has no list, so a field takes the branch, tag or commit. A branch list that fails to load says so and offers the typed field. "Scan again" and "Scan this branch" open the dialog on the card, with that repository and branch chosen. Below the card there is one choice, a "Coverage" segmented control (Focused, Balanced, Exhaustive) that opens on Balanced, with the chosen one's description under it. There is no choice of Skill, and the request carries no `skill`. Under the description, a line says the most credit the audit may hold while it runs; the number is the engine's, read from the per-profile hold of `GET /usage/credit`. The line is absent for an Account on its own key, for a run on a runner, and while the credit has not loaded. One line of chips says where the audit runs, the model and the effort, and "Customize" replaces the chips with the same three as selects: "Run on" appears only for a public repository when a runner is connected. A repository with a queued or running scan shows a warning and disables "Start audit", because the engine allows one active scan per repository. A summary of what is about to run is read to screen readers. In demo screens it never calls the engine and shows "This is a demo, so no audit was started."
